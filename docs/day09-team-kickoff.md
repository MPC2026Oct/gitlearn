## 1. チーム開発編の進め方

9〜14日目は、チーム（3〜4人）で1つのリポジトリを使い、「**サークル紹介ガイドブック**」（`exercises/team-project/`）を共同で作ります。

| 日     | 内容                                           | 集まる？               |
| ------ | ---------------------------------------------- | ---------------------- |
| 9日目  | チームリポジトリに参加、役割決め、Issue の練習 | **集まる**（30分〜）   |
| 10日目 | はじめてのプルリクエスト（メンバー紹介ページ） | 各自のペースで         |
| 11日目 | コードレビュー（担当ページ）                   | 各自のペースで         |
| 12日目 | チームでのコンフリクト練習                     | **集まる**（60〜90分） |
| 13日目 | 最終課題に取り組む                             | 各自のペースで         |
| 14日目 | 完成・リリース・ふりかえり                     | **集まる**（30分〜）   |

- 集まらない日は、各自の都合のよい時間に作業して構いません（非同期）。
- 集まらない日のやりとり（レビューの依頼、質問、「マージしました」の連絡など）は、**Issue やプルリクエスト（Pull Request、略して PR）のコメント** で行います。記録が残るので、あとから見返せます。

## 2. チームリポジトリに参加する

### 招待を承認する

チームリポジトリに push するには、**コラボレーター**（collaborator：共同作業者。リポジトリに書き込む権限 **Write** を持つ人）になる必要があります。運営者が招待を送っているので、それを承認します。

**招待の承認のしかた（どちらか一方）**

- **メールから**：GitHub に登録したメールアドレスに届いた招待メールを開き、**View invitation**（または招待を表示するリンク）をクリックします。
- **URL から**：ブラウザで次の URL を開きます。`<...>` の部分は、かっこごと置き換えてください。

  ```text
  https://github.com/<運営者のアカウント>/gitlearn-team-<チーム記号>/invitations
  ```

招待の画面が開いたら、**Accept invitation** をクリックします（執筆時点の表示です）。

> [!NOTE]
> **運営者が Organization（組織用のアカウント）を使っている場合** は、まず **Organization への招待** が届きます。メールのリンク、または `https://github.com/orgs/<運営者のアカウント>/invitation` を開いて **Join**（参加）してください。チームリポジトリへの権限は、参加後に Organization の設定で付与されます。どちらの方式かは運営者の案内に従ってください。

> [!WARNING]
> リポジトリへの招待は **7日で期限切れ** になります。期限が切れたら運営者に再送を頼んでください。出典：[Self-expiring repository and organization invitations（GitHub Changelog）](https://github.blog/changelog/2020-02-05-self-expiring-repository-and-organization-invitations/)

承認できたか確かめます。

1. ブラウザで `https://github.com/<運営者のアカウント>/gitlearn-team-<チーム記号>` を開きます。
2. リポジトリのページが表示され、招待を承認するよう求める案内が出ていなければ、参加できています（**Settings** タブは見えなくても構いません）。Private のリポジトリで「404」が出る場合は、まだ承認できていません。

> [!IMPORTANT]
> **Public のリポジトリは、招待を承認しなくても開けて、クローンもできます。** 承認しているかは、リポジトリのページ上部に招待の案内（**View invitation** など）が出ていないかで確かめてください。承認しないままだと、10日目の push で `remote: Permission to <運営者のアカウント>/gitlearn-team-<チーム記号>.git denied to ...`（`403`）というエラーになります。

### チームリポジトリをクローンする

8日目と同じ `git clone` で、手元にコピーします。

**Git Bash で**

1. 練習用フォルダの親に移動します。

   ```bash
   cd ~/git-practice
   ```

2. チームリポジトリをクローンします。`<...>` の部分は、かっこごと置き換えてから実行します。

   ```bash
   git clone https://github.com/<運営者のアカウント>/gitlearn-team-<チーム記号>.git
   ```

   （以下の出力例は、チーム記号が `a` の場合です。）

   ```text
   Cloning into 'gitlearn-team-a'...
   remote: Enumerating objects: ...
   ...
   ```

   `~/git-practice/gitlearn-team-<チーム記号>` フォルダができます。

3. VS Code の新しいウィンドウでフォルダを開きます。

   ```bash
   code ~/git-practice/gitlearn-team-<チーム記号>
   ```

4. 新しいウィンドウでターミナルを開き、リモートと状態を確認します。

   ```bash
   cd ~/git-practice/gitlearn-team-<チーム記号>
   git remote -v
   git status
   ```

   ```text
   origin	https://github.com/<運営者のアカウント>/gitlearn-team-a.git (fetch)
   origin	https://github.com/<運営者のアカウント>/gitlearn-team-a.git (push)
   On branch main
   Your branch is up to date with 'origin/main'.

   nothing to commit, working tree clean
   ```

**VS Code で**

1. コマンドパレット（`Ctrl+Shift+P`）で「**Git: クローン**（Git: Clone）」を実行します。
2. URL 欄に `https://github.com/<運営者のアカウント>/gitlearn-team-<チーム記号>.git` を貼り付けて `Enter` を押します。
3. 保存先として `C:\Users\<Windowsのユーザー名>\git-practice` を選びます。
4. 「開く（Open）」をクリックします。

> [!NOTE]
> チームリポジトリも教材のテンプレートから作られているので、中身は自分の `gitlearn` とほぼ同じです。チーム開発編では、その中の **`exercises/team-project/`** フォルダを全員で育てていきます。**自分の `gitlearn` フォルダと間違えないように** 注意してください（VS Code のウィンドウのタイトルで確認できます）。

## 3. 役割を決める

チーム全員で次の表を確認し、自分の役割を決めます。

### 役割記号（A〜D）

**GitHubユーザー名のアルファベット順**（大文字・小文字は区別しない）に、A、B、C、D とします。3人チームは A〜C です。

| 記号 | GitHubユーザー名                |
| ---- | ------------------------------- |
| A    | （アルファベット順で1番目の人） |
| B    | （2番目の人）                   |

## 4. Issue でタスクを管理する

### Issue とは

**Issue** は、「やること」「困っていること」「質問」などを1件ずつ書き込む **チケット（付せん）** です。GitHub のリポジトリごとに用意されていて、次のようなことができます。

- やることを書き出して、**番号（#1、#2 …）** で管理する
- **担当者（Assignees）** を決めて、誰がやるかをはっきりさせる
- **ラベル（Labels）** で種類を分ける
- **コメント** で相談し、やりとりを記録に残す
- 終わったら **Close**（閉じる）して、完了を記録する

チーム開発では、「**作業はすべて Issue から始める**」と決めておくと、誰が何をしているかが一目でわかります。

### テンプレートを使って Issue を作る

練習として、自分用の「**メンバー紹介ページを追加**」Issue を作ります（10日目にこの Issue を使います）。

1. ブラウザでチームリポジトリ（`https://github.com/<運営者のアカウント>/gitlearn-team-<チーム記号>`）を開きます。
2. 上部のタブから **Issues** をクリックします。
3. **New issue** ボタンをクリックします。
4. テンプレートの一覧が表示されるので、「**作業タスク**」を選びます（画面によっては、テンプレート名の横の **Get started** をクリックします）。
5. **Title**（タイトル）に次のように入力します。

   ```text
   メンバー紹介ページを追加（<GitHubユーザー名>）
   ```

   `<GitHubユーザー名>` の部分は、かっこごと自分のユーザー名に置き換えます。

6. 本文（**Description** / 説明欄）には、テンプレートの見出し（やること、完了条件、担当、メモ）が入っています。次のように書き込みます。
   - やること：`exercises/team-project/members/<GitHubユーザー名>.md` を作り、自己紹介を書く
   - 完了条件：PR がマージされ、GitHub 上でページが表示される
   - 担当：自分のユーザー名
7. **Create**（画面によっては **Submit new issue**）をクリックします。
8. Issue のページが開き、タイトルの横に **#番号**（例：`#3`）が付いたことを確かめます。この番号は10日目に使うので覚えておきましょう。

出典：[Creating an issue（GitHub Docs）](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/creating-an-issue)（執筆時点で確認。Issue 作成画面は改修が続いているため、ボタンの名前が変わっている場合があります）

> [!NOTE]
> Issue と PR は同じ番号の列を使います。たとえば #1 が Issue なら、次に作った PR は #2 になります。

### 担当者（Assignees）とラベル（Labels）を付ける

1. 作成した Issue のページの右側にある **Assignees** の歯車（またはその見出し）をクリックします。
2. 自分のユーザー名を選びます（**assign yourself** というリンクがあれば、それをクリックしても構いません）。
3. 同じく右側の **Labels** をクリックします。
4. `documentation`（文書に関する作業）を選びます。
5. 一覧の外をクリックして閉じ、Assignees と Labels に反映されたことを確かめます。

GitHub には最初から次のようなラベルが用意されています（執筆時点）。この勉強会では、新しいラベルは作らず、既定のものを使います。

| ラベル             | 使いどころの例                                     |
| ------------------ | -------------------------------------------------- |
| `documentation`    | ページの追加・修正（ガイドブックの作業はほぼこれ） |
| `bug`              | 表示が崩れている、リンクが切れている               |
| `enhancement`      | 新しいページや機能の追加                           |
| `question`         | 質問                                               |
| `good first issue` | 初めての人向けのかんたんな作業                     |

Organization の設定によっては `documentation` がないことがあります。そのときは運営者に聞くか、ラベルなしで進めます。出典：[Managing labels（GitHub Docs）](https://docs.github.com/en/issues/using-labels-and-milestones-to-track-work/managing-labels)

> [!NOTE]
> Assignees や Labels を変更するには、リポジトリへの書き込み権限が必要です。選べない場合は、招待の承認が済んでいるか確認してください。

### コメントでやりとりする

Issue のページ下部のコメント欄でやりとりします。

1. **ほかのメンバーの「メンバー紹介ページを追加」Issue** を Issues タブから開きます。
2. コメント欄に、次のように書きます。

   ```text
   @hydr4 よろしくお願いします！ ページができたらレビューします。
   ```

   `hydr4` の部分は、コメントする相手のユーザー名にします。`@` に続けて相手のユーザー名を書くと **メンション**（mention）になり、相手に通知が届きます。`@` を入力すると候補が表示されるので、そこから選ぶと確実です。

3. **Comment** ボタンをクリックします。
4. 次に、**自分の Issue** に、コメントで別の Issue を参照してみます。`<Issue番号>` には、さきほどコメントしたメンバーの Issue の番号を、かっこごと置き換えて書きます。

   ```text
   #<Issue番号> と同じように、10日目に PR を出します。
   ```

   `#` に続けて番号を書くと、その Issue（または PR）への **リンク** になります。リンクされた側の Issue にも「この Issue から参照された」と表示されます。

5. **Preview** タブで、表示を確かめてから **Comment** をクリックします。

> [!CAUTION]
> Issue やコメントは、リポジトリにアクセスできる人全員が見られます。個人情報（本名のフルネーム、電話番号、住所、学籍番号、顔写真）や、パスワード・リカバリーコードは絶対に書かないでください。

**VS Code で**：Issue の操作は、基本的に GitHub のブラウザ画面で行います（VS Code の拡張機能「GitHub Pull Requests」でも扱えますが、この勉強会ではブラウザを使います）。

## 5. チームのルールを確認する

チームで気持ちよく作業するために、全チーム共通のルールを決めています。**進行役（9日目は A）** が「チームのルール」Issue を作り、全員がコメントで合意します。

### チームのルール（全チーム共通）

1. `main` に直接 push しない。作業は必ずブランチ → PR。
2. ブランチ名は `<GitHubユーザー名>/<内容>`。
3. PR は作成者以外の1人が承認（Approve）したら、**作成者が** 「Create a merge commit」でマージする。
4. マージしたら GitHub 上のブランチを削除し、手元は `git switch main` → `git pull`。
5. 作業を始める前に `git switch main` → `git pull` で最新にする。
6. 個人情報（本名のフルネーム、電話番号、住所、学籍番号、顔写真）は書かない。

> [!NOTE]
> ルール2の例：GitHubユーザー名が `hydr4` で、メンバー紹介ページを追加するなら `hydr4/add-member-page` です。ブランチ名の `/` はフォルダの区切りのようなもので、「誰の、何の作業か」がひと目でわかります。

### 「チームのルール」Issue を作る（進行役 A）

1. **Issues** → **New issue** をクリックし、テンプレートを使わない空の Issue（**Blank issue** など）を選びます。
2. Title に `チームのルール` と入力します。
3. 本文に、上の「チームのルール」の6項目と、「3. 役割を決める」で決めた **役割記号とユーザー名の表** を書きます（[演習](../exercises/day09-team-kickoff/README.md) に本文の例文があります）。
4. **Create**（または **Submit new issue**）をクリックします。

### 合意のコメントをする（全員）

1. 「チームのルール」Issue を開きます。
2. ルールと役割を読み、問題がなければ次のようにコメントします。

   ```text
   ルールと役割を確認しました。合意します！（記号：B）
   ```

3. 全員のコメントがそろったことを、進行役が確認します。

> [!TIP]
> 疑問や提案があれば、遠慮なくコメントで質問しましょう。Issue は「決めたことの記録」になります。

## よくあるつまずき

**症状：招待メールが届かない**
- 原因：GitHub に登録したメールアドレスと別のアドレスを確認している、または迷惑メールに入っている。
- 対処：`https://github.com/<運営者のアカウント>/gitlearn-team-<チーム記号>/invitations` を直接開きます。GitHub の右上の通知（ベルのアイコン）に届いていることもあります。→ [レシピ github-02](../recipes/github.md#github-02)

**症状：招待の URL を開くと 404 になる**
- 原因：招待がまだ送られていない、期限（7日）が切れた、または別の GitHubアカウントでサインインしている。
- 対処：右上のアイコンでサインイン中のアカウントを確認し、運営者に招待の状況を聞きます。

**症状：`git clone` で `remote: Repository not found.` と出る**
- 原因：招待を承認していない（Private のリポジトリの場合。Public なら承認前でもクローンできますが、10日目の push で `403` になります）、URL を打ち間違えた、または別のアカウントの認証情報が保存されている。
- 対処：ブラウザでリポジトリが開けるか確かめ、URL を見比べます。→ [レシピ remote-01](../recipes/remote.md#remote-01)

**症状：`fatal: destination path 'gitlearn-team-a' already exists and is not an empty directory.` と出る**
- 原因：同じ名前のフォルダがすでにあります（前に一度クローンした）。
- 対処：そのフォルダをそのまま使います。`cd ~/git-practice/gitlearn-team-<チーム記号>` → `git pull` で最新にしてください。

**症状：Issue の Assignees や Labels を変更できない**
- 原因：書き込み権限（Write）がない、または招待を承認していない。
- 対処：招待を承認したか確かめ、運営者に権限を確認してもらいます。→ [レシピ github-04](../recipes/github.md#github-04)

**症状：テンプレートの一覧に「作業タスク」が出てこない**
- 原因：チームリポジトリに `.github/ISSUE_TEMPLATE/` がない（運営者がテンプレートから作っていない）可能性があります。
- 対処：運営者に連絡します。とりあえずは空の Issue に「やること」「完了条件」「担当」を自分で書いて作ります。
