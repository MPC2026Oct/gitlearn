# レビューチェックリスト

PR をレビューするときの観点と、コメントの例文です。説明ページ：[11日目：コードレビュー](../../docs/day11-code-review.md)

## 心がけ

- 見るのは「人」ではなく「変更」です。
- 具体的に書きます（どこを、どうしたらよいか）。
- 良いところも1つは書きます。
- 迷ったら、まず質問の形で書きます。

## 観点

- [ ] **目的に合っているか**：PR の説明と Issue の完了条件に、変更が合っている
- [ ] **誤字・脱字がないか**：漢字の変換ミス、送り仮名、表記ゆれ
- [ ] **リンク切れがないか**：リンクをクリックして、ちゃんと開く
- [ ] **プレビューで正しく表示されるか**：見出し、リスト、表が崩れていない（Files changed の **Display the rich diff**、または VS Code のプレビュー）
- [ ] **個人情報が入っていないか**：本名のフルネーム、電話番号、住所、学籍番号、顔写真
- [ ] **言葉づかいが適切か**：誰が読んでもやさしい表現になっている
- [ ] **関係のない変更が混ざっていないか**：Files changed に、目的と関係ないファイルがない

## コメントの例文

### 良いところを伝える

- 「見出しが整理されていて、とても読みやすいです。」
- 「新入生が不安に思いそうな点が先に書かれていて、親切だと思いました。」

### 直してほしい点を伝える

- 「3行目の『活動日』が『活動日び』になっています。」
- 「ここのリンクが開けませんでした。URL を確認してもらえますか？」
- 「この行に電話番号が書かれています。個人情報になるので、削除をお願いします。」

### 質問する

- 「この日程は、毎年同じですか？ もしそうなら、『毎年』と書いても良さそうです。」
- 「この部分の意図を教えてもらえますか？」

### 修正を提案する（Suggested changes）

行コメントの「修正提案を追加（Add a suggestion）」を押すと、書き換え案を提示できます。取り込む側は **Commit suggestion** を押すだけで反映できます。

- 「誤字なので、提案を付けました。そのまま取り込んでください。」

### Approve するとき

- 「確認しました。問題ありません。Approve します。」
- 「直していただき、ありがとうございます。Approve します。」

## レビューの種類

| 種類 | 使う場面 |
|---|---|
| Comment | 感想や質問だけを伝えたい |
| Approve | マージしてよいと判断した |
| Request changes | 直してもらわないとマージできない点がある |
