# よいコミットとレビューしやすい PR

[Appendix の目次](README.md) ｜ [README（全体の地図）](../README.md)

> **この解説の対象**：[4日目「差分・履歴・.gitignore」](../docs/day04-diff-log-ignore.md) を読んだ人（プルリクエスト（Pull Request、略して PR）の節は [11日目「コードレビュー」](../docs/day11-code-review.md) の後に）
>
> **読む時間の目安**：約25分（手を動かして試す場合は +10分）

4日目では「1つのコミットには1つの目的」「メッセージは何をしたかを短く」と学びました。このページでは、その理由をもう少し掘り下げ、**1つのファイルの中の変更を分けてコミットする方法**、**本文つきのコミットメッセージの書き方**、よく使われる書式の **Conventional Commits**、そして **レビューしやすい PR** の作り方を紹介します。

## このページでわかること

- コミットの単位をそろえると、何が楽になるのか
- 1つのファイルの中の変更を、目的ごとに分けてステージする方法（`git add -p`、VS Code の行単位のステージ）
- コミットメッセージの構造（1行目の要約・空行・本文）と、日本語での書き方の例
- Conventional Commits（`feat:` `fix:` `docs:` などの書式）の概要
- PR の大きさの目安と、レビューしやすい PR の書き方

## 1. なぜコミットの単位とメッセージが大事なのか

コミットは「後から読まれる記録」です。読むのは、数週間後の自分や、チームの仲間、レビュアーです。コミットの単位とメッセージがそろっていると、次のようなことが楽になります。

| 場面 | 単位がそろっていると | ばらばらだと |
|---|---|---|
| 履歴を読む（`git log --oneline`） | 1行ずつ読むだけで、何が起きたかわかる | 「更新」「修正」が並び、中身を1つずつ開かないとわからない |
| 取り消す（`git revert`） | 問題のコミットだけを打ち消せる | 関係ない変更まで一緒に消えてしまう（[Appendix：取り消しの詳細](undo-in-depth.md#revert-vs-reset)） |
| 原因を探す | 「いつ、なぜこの行が変わったか」がメッセージでわかる | 変わったことはわかっても、理由がわからない |
| レビューする | 変更の意図ごとに確認できる | 誤字修正と内容の変更が混ざり、見落としが増える |

> [!TIP]
> ファイルの各行を最後に変えたコミットは、`git blame <ファイル名>`（例：`git blame profile.md`）で調べられます。VS Code では、行をクリックすると行末に最後の変更のコミットがうすく表示されることがあります（執筆時点の表示です。設定によって異なります）。どちらも、メッセージがわかりやすいほど役に立ちます。

## 2. よいコミットの単位

### 1つの目的に1コミット

目安は、**「このコミットは何をしたか」を1文で言えること** です。1文に「と」や「、」が入ったら、分けられないか考えてみましょう。

| 状況 | よくない例 | よい例 |
|---|---|---|
| 誤字の修正と内容の追加を同時にした | 「自己紹介を更新」（1コミット） | 「自己紹介の誤字を修正」「好きなことに散歩を追加」（2コミット） |
| 見出しの名前を変え、それに合わせてリンクも直した | 「見出しを変更」と「リンクを修正」を別々のコミットにし、間の状態ではリンクが切れている | 「活動紹介の見出しを変更し、リンクを更新」（1コミット。片方だけだと壊れた状態になるため） |
| 1週間分の作業 | 金曜日にまとめて1コミット | 意味のあるまとまりができるたびにコミット |

2つ目の例のように、「分けると途中の状態が壊れる」場合は、1つのコミットにまとめるほうがよいこともあります。プログラムなら「途中のコミットでも動く」、この教材の Markdown なら「途中のコミットでもプレビューが崩れない・リンクが切れない」ことを目安にします。

### 大きすぎず、小さすぎず

- **大きすぎる**：複数の目的が混ざる。取り消しやレビューが難しくなる。
- **小さすぎる**：「1文字直した」コミットが10個並ぶと、かえって読みにくい。push 前なら、対話的 rebase でまとめられます（[Appendix：rebase](rebase.md#interactive)）。直前のコミットに入れ忘れただけなら `git commit --amend` で足せます（[レシピ undo-03](../recipes/undo.md#undo-03)）。

## 3. 1つのファイルの中の変更を分けてコミットする

4日目では、ファイルごとに `git add` を分けてコミットしました。では、**1つのファイルの中に、目的の違う変更が2つある** ときはどうすればよいでしょうか。Git では、ファイルの一部（変更のかたまり）だけをステージできます。

### 実験用のリポジトリを用意する

1. 次のコマンドで、自己紹介のファイルを1つ持つリポジトリを作ります。

```bash
mkdir -p ~/git-practice/appendix-lab/commit
cd ~/git-practice/appendix-lab/commit
git init
printf '# 自己紹介\n\n- ニックネーム: たいち\n- 好きなこと: 読書\n- 出身: 東京\n- 目標: Git に慣れる\n- ひとこと: よろしく\n' > profile.md
git add profile.md
git commit -m "自己紹介を作成"
```

> [!TIP]
> `git add` などで `LF will be replaced by CRLF` という警告が出ることがありますが、無視してかまいません（`printf` や `echo` で作ったファイルは改行コードが LF になるため。[改行コードと文字コード](line-endings-and-encoding.md#lf-will-be-replaced)、[レシピ trouble-11](../recipes/troubleshooting.md#trouble-11)）。

2. 目的の違う2つの変更を加えます（「好きなこと」の追加と、「ひとこと」の言い回しの変更）。

```bash
sed -i 's/読書/読書と散歩/' profile.md
sed -i 's/よろしく/よろしくお願いします/' profile.md
git diff
```

```text
@@ -1,7 +1,7 @@
 # 自己紹介
 
 - ニックネーム: たいち
-- 好きなこと: 読書
+- 好きなこと: 読書と散歩
 - 出身: 東京
 - 目標: Git に慣れる
-- ひとこと: よろしく
+- ひとこと: よろしくお願いします
```

作り直したいときは、エクスプローラーで `C:\Users\<Windowsのユーザー名>\git-practice\appendix-lab\commit` フォルダを削除してから、もう一度実行してください。

### Git Bash で：`git add -p`

`git add -p`（`--patch`）は、変更のかたまり（hunk：ハンク）ごとに「ステージするか」を聞いてくれるコマンドです。

1. 実行します。

```bash
git add -p
```

```text
@@ -1,7 +1,7 @@
 # 自己紹介
 ...
(1/1) Stage this hunk [y,n,q,a,d,s,e,p,P,?]?
```

（表示される文字は Git のバージョンによって少し違います。ここでは Git 2.56 の表示です）

2. 2つの変更が近いので、1つのかたまりとして表示されました。`s`（split：分割）と入力して Enter を押します。

```text
Split into 2 hunks.
...
-- 好きなこと: 読書
+- 好きなこと: 読書と散歩
...
(1/2) Stage this hunk [y,n,q,a,d,K,j,J,g,/,e,p,P,?]?
```

3. 1つ目（好きなこと）はステージしたいので `y` と入力して Enter を押します。
4. 2つ目（ひとこと）が表示されたら、今回はステージしないので `n` と入力して Enter を押します。

よく使う答えは次の4つです（`?` を入力すると全部の説明が出ます）。

| 入力 | 意味 |
|---|---|
| `y` | このかたまりをステージする |
| `n` | このかたまりはステージしない |
| `s` | かたまりをさらに小さく分ける（分けられるときだけ表示される） |
| `q` | ここでやめる（ここまでの答えは反映される） |

5. 状態を確かめます。

```bash
git status --short
git diff --staged
```

```text
MM profile.md
```

`MM` は「ステージにも（左の列）、ワーキングツリーにも（右の列）変更がある」という意味です。1つのファイルの変更が、ステージされた部分とされていない部分に分かれました（[Appendix：3つの場所](three-areas.md)）。`git diff --staged` には「好きなこと」の変更だけが表示されます。

6. 目的ごとにコミットします。

```bash
git commit -m "好きなことに散歩を追加"
git add profile.md
git commit -m "ひとことを丁寧な言い方に変更"
git log --oneline
```

```text
b2c4e6a (HEAD -> main) ひとことを丁寧な言い方に変更
9a1d3f5 好きなことに散歩を追加
4e8f0c2 自己紹介を作成
```

（ハッシュ値は人によって違います）

### VS Code で：行を選んでステージする

1. ソース管理ビューで、変更したファイル名をクリックして差分（diff）を開きます。
2. 右側（変更後）で、ステージしたい行を選択します。
3. 選択した範囲を右クリックし、**選択した範囲をステージする**（Stage Selected Ranges）を選びます。差分の左の余白（ガター）に出るステージ用のボタンを使うこともできます（出典：[VS Code Docs: Staging, Commits & Undo](https://code.visualstudio.com/docs/sourcecontrol/staging-commits)。執筆時点の表示です）。
4. ソース管理ビューの「ステージされている変更（Staged Changes）」と「変更（Changes）」の両方に同じファイルが表示されれば、分けてステージできています。

## 4. コミットメッセージの書き方

### メッセージの構造

コミットメッセージは、次の3つの部分でできています。

```text
好きなことに散歩を追加                         ← 1行目：要約（タイトル）
                                               ← 2行目：空行
週末によく散歩しているので、自己紹介にも         ← 3行目以降：本文（なぜ・何を・補足）
書いておくことにした。
```

git-commit のドキュメントは、「必須ではないが、変更を要約した短い1行（50文字以内）で始め、空行を1行入れてから、詳しい説明を書くとよい」としています。最初の空行までがコミットの **タイトル** として扱われ、`git log --oneline` や GitHub の画面など、Git のあらゆる場所で使われます（出典：[git-commit の DISCUSSION](https://git-scm.com/docs/git-commit)）。

「50文字」は英語（半角）での目安です。日本語の全角文字は半角2文字分の幅で表示されることが多いため、この勉強会では4日目と同じく **20〜30文字くらい** を目安にしています。

### 1行目（要約）のコツ

| コツ | よくない例 | よい例 |
|---|---|---|
| 何をしたかが具体的にわかる | `修正` | `FAQ の入会費用の誤りを修正` |
| 対象（どのページの、どこか）を入れる | `追記` | `年間行事に学園祭を追加` |
| 「〜を追加」「〜を修正」のように、体言止めでそろえる | `学園祭を追加しました。` | `年間行事に学園祭を追加` |
| 1行に複数の目的を詰め込まない | `誤字修正と行事追加とリンク修正` | コミットを分ける |

英語で書くプロジェクトでは、`Add festival to events page` のように **命令形**（動詞の原形で始める）で書くのが一般的です。

### 本文には「なぜ」を書く

「何を変えたか」は差分を見ればわかりますが、**「なぜ変えたか」は書かないと残りません**。本文は、次のようなときに書きましょう。

- 変更の理由が差分だけではわからないとき（「部長と相談して、集合時間を早めた」）
- あえて選ばなかった方法があるとき（「表にすることも考えたが、スマホで見づらいので箇条書きにした」）
- 関連する Issue（イシュー：課題やタスクを書き込むチケット） があるとき（「#12 の議論を反映」）

### 本文つきのメッセージを書く方法

**方法1：`-m` を2回使う**

`-m` を複数書くと、それぞれが別の段落（間に空行が入る）になります。

```bash
git commit -m "集合時間を10時に変更" -m "部長と相談し、準備の時間を取るために30分早めた。"
```

**方法2：`-m` なしでエディタを使う**

`git commit` とだけ実行すると、1日目に設定した VS Code（`core.editor`）でメッセージ用のファイルが開きます。1行目に要約、1行空けて本文を書き、保存してタブを閉じるとコミットされます。`#` で始まる行は無視されます。

**方法3：VS Code のメッセージ欄**

ソース管理ビューのメッセージ欄では、Enter で改行できます。1行目に要約を書き、空行を入れてから本文を書いて、「コミット（Commit）」ボタンを押します。

### 書いたメッセージを確かめる

```bash
git log -1
```

```text
commit 3d8c9eaee6316a0ca812def699db1657763d117d (HEAD -> main)
Author: 表示したい名前 <ID+ユーザー名@users.noreply.github.com>
Date:   ...

    集合時間を10時に変更

    部長と相談し、準備の時間を取るために30分早めた。
```

`git log --oneline` では1行目だけが表示されることも確かめてみてください。

## 5. Conventional Commits：メッセージの書式の決まり

オープンソースや仕事の現場では、メッセージの先頭に **種類** を付ける **Conventional Commits** という書式がよく使われます（出典：[Conventional Commits 1.0.0（日本語版）](https://www.conventionalcommits.org/ja/v1.0.0/)）。

```text
<型>[任意のスコープ]: <説明>

[任意の本文]

[任意のフッター]
```

| 型（type） | 意味 | 例 |
|---|---|---|
| `feat` | 新しい機能（内容）を追加 | `feat: FAQ ページを追加` |
| `fix` | 誤りの修正 | `fix: 年間行事の日付の誤りを修正` |
| `docs` | ドキュメントだけの変更 | `docs: README の目次を更新` |
| `style` | 意味を変えない見た目の修正（空白、書式など） | `style: 見出しの前後の空行をそろえる` |
| `refactor` | 機能を変えない作り直し | `refactor: メンバー一覧を表に書き換え` |
| `chore` | その他の雑務（設定ファイルなど） | `chore: .gitignore に OS のファイルを追加` |

- 仕様で決まっているのは `feat` と `fix` だけで、ほかの型は「よく使われる例」として紹介されています。
- `feat(faq): 入会費用の質問を追加` のように、かっこで **スコープ**（変更の範囲）を付けられます。
- 互換性を壊す大きな変更は、`feat!:` のように `!` を付けるか、フッターに `BREAKING CHANGE:` と書きます。
- 書式がそろっていると、変更履歴（リリースノート）の自動作成やバージョン番号の自動決定などに使えます。

この勉強会では Conventional Commits は **使いません**（日本語で「何をしたか」を短く書くルールです）。チームやプロジェクトによってルールが違うので、参加するときは、まずそのリポジトリの `git log --oneline` や `CONTRIBUTING.md` を見て、合わせるのがよい習慣です。

## 6. レビューしやすい PR

### 小さく、1つの目的に

GitHub Docs は、「小さく焦点の絞られた PR は、レビューしやすく、マージしても安全」としています。大きくなった変更は、目的ごとに複数の PR に分けることを勧めています（出典：[Helping others review your changes](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/getting-started/helping-others-review-your-changes)）。

PR の大きさに公式な上限はありませんが、この勉強会の目安は次のとおりです。

| 目安 | 説明 |
|---|---|
| 1 Issue = 1 ブランチ = 1 PR | 13日目のルール。PR のタイトルを見れば、どの Issue の作業かわかる |
| 変更するファイルは数個まで | 「Files changed」をひと通り読むのに10分程度で済む量 |
| 関係ない修正を混ぜない | 作業中に別のページの誤字を見つけたら、別の Issue・PR にする（または Issue にメモしておく） |

PR が大きいほどレビューは大ざっぱになり、見落としが増えます。また、作業期間が長い PR ほど `main` との差が開き、コンフリクトも起きやすくなります（12日目の「コンフリクトを減らす習慣」）。

### タイトルと本文

- **タイトル**：コミットメッセージの1行目と同じく、「何をしたか」を具体的に。例：`年間行事ページを作成`
- **本文**：このリポジトリの PR テンプレート（`.github/pull_request_template.md`）の項目を埋めます。
  - **関連する Issue**：`Closes #<Issue番号>`（[Appendix：GitHub でのチーム開発](github-collaboration.md#closing-keywords)）
  - **変更内容**：何を、なぜ変えたか
  - **確認したこと**：プレビューで表示を確かめた、など
  - **レビューしてほしい点**：特に見てほしいところ、迷っているところ。レビュアーがどこから読めばよいか迷わないようにします

### 出す前に自分でレビューする

PR を作ったら、レビューを頼む前に、自分で **Files changed** タブを上から下まで読みましょう。GitHub Docs も、自分の PR を先にレビューすることで、ミスを早く見つけられると勧めています。

- 関係ないファイルや、意図しない変更（空白だけの変更、消すつもりのなかった行）が入っていないか
- 個人情報が入っていないか
- プレビューで表示が崩れていないか、リンクが切れていないか

[11日目のレビュー観点](../exercises/day11-review/review-checklist.md) を、自分の PR に当てはめてみるのも効果的です。

### まだ途中の PR は「ドラフト」で

早めに方向性を見てもらいたいけれど、まだ完成していないときは、PR を作るときに **Create draft pull request** を選ぶと、ドラフト PR になります。ドラフトのうちはマージできず、準備ができたら **Ready for review** を押して通常の PR にします（執筆時点の表示です）。

### PR のコミットはどう残るか

PR の中のコミットが `main` にどう残るかは、マージ方法で変わります。この教材の **Create a merge commit** では、PR の中のコミットがそのまま `main` の履歴に残ります。だからこそ、PR の中のコミットも「1つの目的に1コミット」でそろえておく価値があります（Squash and merge の場合は、PR 全体が1つのコミットにまとめられます。[Appendix：GitHub でのチーム開発](github-collaboration.md#merge-methods)）。

---

## まとめ

- コミットは後から読まれる記録。1つの目的に1コミットにすると、読む・取り消す・レビューするのが楽になる。
- 1つのファイルの中の変更も、`git add -p` や VS Code の **選択した範囲をステージする**（Stage Selected Ranges）で分けてコミットできる。
- メッセージは「1行目に要約、空行、本文に理由」。この勉強会では日本語で20〜30文字くらいの要約を書く。
- Conventional Commits は `feat:` `fix:` などの型を付ける書式。プロジェクトのルールに合わせて使う。
- PR は小さく、1つの目的に。タイトル・本文・自分でのレビューで、レビュアーの負担を減らす。
