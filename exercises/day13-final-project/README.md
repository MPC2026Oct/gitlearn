# 13日目の演習：最終課題「サークル紹介ガイドブック」

説明ページ：[13日目：最終課題に取り組む](../../docs/day13-final-project.md)

## 目的

ガイドブックを完成させるための作業を Issue に分け、1 Issue = 1 ブランチ = 1 PR で並行して進めます。

## 所要時間の目安

90分（各自のペースで進めて構いません）

## 最終課題の仕様

チームリポジトリの `exercises/team-project/` に、サークル紹介ガイドブックを完成させます。

```text
exercises/team-project/
├── README.md              表紙と目次
├── schedule.md            活動予定（確定版）
├── retrospective.md       ふりかえり（14日目）
├── members/
│   ├── README.md          メンバー一覧
│   ├── _template.md       紹介ページのひな形
│   └── <GitHubユーザー名>.md   各メンバーの紹介ページ（10日目に作成済み）
└── pages/
    ├── activities.md      活動紹介（11日目・A）
    ├── events.md          年間行事（11日目・B）
    ├── faq.md             よくある質問（11日目・C）
    ├── newcomers.md       新入生へ（11日目・D／3人チームは今日）
    └── git-glossary.md    チームで作る Git 用語集
```

### 完成条件

- [ ] 下の表の作業の Issue（作業4は1人1件。4人チームは作業3なしで8件、3人チームも8件）がすべて Close されている
- [ ] 表紙 `README.md` から、すべてのページへリンクでたどれる
- [ ] GitHub 上の `main` で表示したとき、表示が崩れていない
- [ ] 個人情報が入っていない

## 手順

### 1. Issue に分ける（進行役）

13日目の進行役（4人チームは A、3人チームは B）が、次の作業を Issue にします（「作業タスク」テンプレート）。担当はチームで相談して決めます。

| # | 作業 | 備考 |
|---|---|---|
| 1 | 表紙 `team-project/README.md` の目次を完成させ、全ページへリンクする | |
| 2 | `members/README.md` に全員の紹介ページへのリンクを載せる | |
| 3 | `pages/newcomers.md` を完成させる | **3人チームのみ**（4人チームは D が11日目に作成済み） |
| 4 | `pages/git-glossary.md` に、各自が3語ずつ用語を追加する | **全員が担当。Issue は1人1つ作る**（例：「用語集に3語追加（hanako）」）。同じファイルを編集するのでコンフリクトが起きうる（12日目の復習） |
| 5 | 各ページの末尾に「目次へ戻る」リンク（`[目次へ戻る](../README.md)`）を付ける | 担当を決めて **1人で**、ほかの作業が終わってから行う。`schedule.md` は `[目次へ戻る](README.md)`。`members/README.md` は最初から付いている |
| 6 | `schedule.md` を確定版に整える | 12日目に残した複数案から1つに決める |

### 2. 並行して作業する

各自が自分の Issue について、次の流れを回します。`<...>` の部分は、かっこごと置き換えてから実行します。

```bash
cd ~/git-practice/gitlearn-team-<チーム記号>
git switch main
git pull
git switch -c <GitHubユーザー名>/<内容>
```

ブランチ名の `<内容>` は、説明ページと同じ次の名前にそろえます。

| 作業 | ブランチ名 |
|---|---|
| 1 表紙の目次 | `<GitHubユーザー名>/toc` |
| 2 メンバー一覧 | `<GitHubユーザー名>/members-list` |
| 3 新入生へ | `<GitHubユーザー名>/newcomers` |
| 4 用語集 | `<GitHubユーザー名>/glossary` |
| 5 目次へ戻るリンク | `<GitHubユーザー名>/back-links` |
| 6 活動予定 | `<GitHubユーザー名>/schedule` |

- 1つの Issue に、1つのブランチ、1つの PR。
- PR には `Closes #<Issue番号>` を入れ、組の相手にレビューしてもらいます。
- 作業中のブランチが長くなるときは、こまめに `main` の最新を取り込みます。

  ```bash
  git fetch origin
  git merge origin/main
  ```

  コンフリクトがなくても、VS Code にマージコミットのメッセージのタブが開き、ターミナルが待ち状態になります。そのままタブを閉じるとマージが終わります。

### 3. 用語集のコンフリクトに備える（作業4）

- `git-glossary.md` は、全員が同じファイルの同じ位置（末尾付近）に追加するため、コンフリクトが起きることがあります。起きたら、12日目と同じ方法で **全員の用語を残して** 解決します。
- 用語は、7日目までに学んだ言葉など、自分がつまずいた言葉から選ぶと、後で読み返しやすくなります。

### 4. 進み具合を確かめる

```bash
git switch main
git pull
git log --oneline --graph --all
```

GitHub の **Issues** 一覧で、Open の件数が減っているかも見ます。

## 完了条件（この日の）

- [ ] 作業の Issue が作られ、担当が決まっている（作業4は1人1件として、4人チームは8件（作業3なし）、3人チームは8件）
- [ ] 自分の担当の PR が Merged になっている
- [ ] 自分が `git-glossary.md` に3語を追加した（`main` に載っている）
- [ ] `main` の最新で `git log --oneline --graph --all` を見て、PR のマージが履歴に表れていることを確認した

## ヒント

- 担当は、1人に偏らないようにします。作業が小さい人は、他の人の PR のレビューを積極的に引き受けましょう。
- 他の人の PR が先にマージされたら、自分のブランチに `main` を取り込んでから続きを書くと、コンフリクトが起きにくくなります。
- 発展（任意）：[rebase-optional.md](rebase-optional.md) で、rebase を試せます。**共有しているブランチでは使いません。**
- 詳しくは [レシピ集（GitHub）](../../recipes/github.md) を見てください。
